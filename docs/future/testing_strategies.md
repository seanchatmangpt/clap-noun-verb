# Advanced Testing Strategies for clap-noun-verb CLI Systems

**Status:** Proposed for v6.0 (Phase 1–2)  
**Timeline:** 2026-06-01 – 2026-06-29

This guide details the advanced testing strategies designed for `clap-noun-verb` command-line interfaces. Building on the Chicago TDD (Classical TDD) philosophy of state-based testing with real collaborators, this guide covers advanced methodologies required for resilient, production-ready, and self-verifying CLI applications.

---

## 1. Reflexive Testing (Self-Testing Systems)

Reflexive testing refers to a CLI's capability to verify its own correctness, invariants, and performance benchmarks at runtime or compile-time, often driven by property-based testing and metadata defined in RDF ontologies.

### Core Concepts

`clap-noun-verb` utilizes a type-first design to enforce test generation invariants:
*   **`TestCase<T>`**: Represents a type-safe test case encoding capability combinations and expected behavior (`Assertion`).
*   **`CoverageMask<const N: usize>`**: A bitset of size `N` that tracks covered capability combinations at compile time with zero runtime overhead.
*   **`RegressionBaseline<const N: usize>`**: A zero-cost performance baseline comparison tool utilizing const generics to track execution times and flag performance regressions.
*   **`SemanticTestGenerator`**: Parsers that discover capability combinations declared in Turtle (`.ttl`) RDF ontologies to construct valid execution paths.

### Compile-Time and Runtime Reflexive Testing Pattern

Reflexive testing allows the CLI itself to expose a `selftest` or `verify` command.

```rust
use clap::{Parser, Subcommand};
use proptest::prelude::*;
use std::collections::HashMap;

#[derive(Parser)]
#[command(name = "my-cli", about = "Reflexive Testing CLI")]
pub struct Cli {
    #[command(subcommand)]
    pub command: Option<Commands>,
}

#[derive(Subcommand)]
pub enum Commands {
    /// Perform reflexive self-tests directly from the CLI binary
    Selftest {
        #[arg(long, default_value = "100")]
        iterations: u32,
    },
}

/// Type-safe assertion definitions for testing
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum Assertion {
    Succeeds,
    FailsWith(String),
}

/// A representation of a reflexive test case
pub struct TestCase {
    pub id: String,
    pub capabilities: Vec<String>,
    pub assertion: Assertion,
}

impl TestCase {
    pub fn verify(&self) -> Result<(), String> {
        // Execute and assert state changes or output matches
        match &self.assertion {
            Assertion::Succeeds => {
                // Perform check...
                Ok(())
            }
            Assertion::FailsWith(expected_err) => {
                // Perform failing check and assert error contains expected_err
                Ok(())
            }
        }
    }
}
```

### Parsing Metadata (Turtle Ontologies) for Test Generation

Using semantic models, tests are generated by extracting valid paths from capabilities defined in ontologies:

```rust
pub struct SemanticTestGenerator {
    ontology: String,
}

impl SemanticTestGenerator {
    pub fn new(ontology: String) -> Self {
        Self { ontology }
    }

    pub fn extract_capabilities(&self) -> Vec<String> {
        let mut capabilities = Vec::new();
        for line in self.ontology.lines() {
            let trimmed = line.trim();
            if trimmed.contains("cnv:hasCapability") {
                if let Some(cap) = trimmed.split("cnv:hasCapability").nth(1) {
                    let cleaned = cap.trim_matches(|c| c == ' ' || c == ';' || c == '.');
                    capabilities.push(cleaned.to_string());
                }
            }
        }
        capabilities
    }
}
```

## 2. Testing Interactive Prompts

Testing interactive prompts (such as Wizards, interactive shell loops, or confirmation dialogs) requires decoupling stdio from the physical terminal using asynchronous mock streams.

### Utilizing Mock Readers and Writers

The `clap-noun-verb` framework employs `AsyncReader` and `AsyncWriter` over generic buffers to simulate standard input and output streams.

```rust
use tokio::io::{AsyncReadExt, AsyncWriteExt};
use std::io::Result;

pub struct InteractiveSession<R, W> {
    reader: R,
    writer: W,
}

impl<R, W> InteractiveSession<R, W>
where
    R: tokio::io::AsyncRead + Unpin,
    W: tokio::io::AsyncWrite + Unpin,
{
    pub fn new(reader: R, writer: W) -> Self {
        Self { reader, writer }
    }

    pub async fn run_prompt(&mut self, question: &str) -> Result<String> {
        self.writer.write_all(question.as_bytes()).await?;
        self.writer.flush().await?;

        let mut buffer = [0; 1024];
        let bytes_read = self.reader.read(&mut buffer).await?;
        let input = String::from_utf8_lossy(&buffer[..bytes_read]);
        Ok(input.trim().to_string())
    }
}
```

### Simulating Partial Streaming Inputs and Interruptions

To verify behavior when the user pastes multi-line scripts or experiences connection drops / timeouts during interactive wizard steps, use `tokio::time::timeout` and incremental chunks.

```rust
#[cfg(test)]
mod tests {
    use super::*;
    use std::time::Duration;

    #[tokio::test]
    async fn test_interactive_session_success() {
        let input_data = b"yes\n";
        let mut output_buffer = Vec::new();

        let mut session = InteractiveSession::new(&input_data[..], &mut output_buffer);
        let answer = session.run_prompt("Are you sure? ").await.unwrap();

        assert_eq!(answer, "yes");
        assert_eq!(String::from_utf8(output_buffer).unwrap(), "Are you sure? ");
    }

    #[tokio::test]
    async fn test_stream_timeout_handling() {
        // Simulating a slow reader stream that doesn't send delimiter within timeout window
        let slow_input = tokio_test::io::Builder::new()
            .wait(Duration::from_millis(200))
            .read(b"slow input")
            .build();
        let mut output_buffer = Vec::new();

        let mut session = InteractiveSession::new(slow_input, &mut output_buffer);
        
        let result = tokio::time::timeout(
            Duration::from_millis(50), 
            session.run_prompt("Wait: ")
        ).await;

        assert!(result.is_err(), "Expected timeout when input is delayed");
    }
}
```

## 3. Mocking Environment States

Mocking system parameters like environment variables, configuration files, and terminal attributes must be handled carefully in Rust due to test concurrency constraints.

### Thread-Safe Environment Variable Mocking

Because Rust runs tests concurrently in the same process, calling `std::env::set_var` can lead to race conditions, flakiness, and crashes. Use the following mitigation strategies:

#### Strategy A: Dependency Injection of Env Settings (Recommended)

Rather than checking `std::env::var` directly in deep business logic, inject a configuration provider.

```rust
pub trait EnvLoader {
    fn get_var(&self, key: &str) -> Result<String, std::env::VarError>;
}

pub struct SystemEnvLoader;

impl EnvLoader for SystemEnvLoader {
    fn get_var(&self, key: &str) -> Result<String, std::env::VarError> {
        std::env::var(key)
    }
}

pub struct MockEnvLoader {
    variables: std::collections::HashMap<String, String>,
}

impl EnvLoader for MockEnvLoader {
    fn get_var(&self, key: &str) -> Result<String, std::env::VarError> {
        self.variables
            .get(key)
            .cloned()
            .ok_or(std::env::VarError::NotPresent)
    }
}
```

#### Strategy B: Serialized Execution with Test Mutexes

If modifying actual system process variables is unavoidable, synchronize tests using a static `Mutex` to serialize environment-dependent tests.

```rust
use std::sync::Mutex;
use lazy_static::lazy_static;

lazy_static! {
    static ref ENV_MUTEX: Mutex<()> = Mutex::new(());
}

#[test]
fn test_with_env_var() {
    let _guard = ENV_MUTEX.lock().unwrap();
    std::env::set_var("API_KEY", "test_key");
    
    // Act
    let val = std::env::var("API_KEY").unwrap();
    assert_eq!(val, "test_key");
    
    // Cleanup
    std::env::remove_var("API_KEY");
}
```

### File System Mocking and Temporary Directory Isolation

To isolate configuration file reads/writes, leverage `tempfile::TempDir` or `tempfile::NamedTempFile`. Ensure the application's config directory path can be overridden.

```rust
use std::path::{Path, PathBuf};

pub struct ConfigManager {
    base_path: PathBuf,
}

impl ConfigManager {
    pub fn new(base_path: PathBuf) -> Self {
        Self { base_path }
    }

    pub fn config_path(&self) -> PathBuf {
        self.base_path.join("config.toml")
    }

    pub fn write_config(&self, content: &str) -> std::io::Result<()> {
        std::fs::write(self.config_path(), content)
    }
}

#[cfg(test)]
mod fs_tests {
    use super::*;
    use tempfile::tempdir;

    #[test]
    fn test_isolated_config_writing() {
        let temp = tempdir().unwrap();
        let manager = ConfigManager::new(temp.path().to_path_buf());

        manager.write_config("port = 8080").unwrap();
        
        let path = manager.config_path();
        assert!(path.exists());
        let read = std::fs::read_to_string(path).unwrap();
        assert_eq!(read, "port = 8080");
    }
}
```

### Mocking Terminal/Tty Capabilities

To test how your CLI reacts when piped to another tool vs being executed in an interactive terminal (TTY):
1.  Isolate your terminal detection calls.
2.  Use traits to mock whether stdout is a TTY.

```rust
pub trait TerminalDetector {
    fn is_stdout_tty(&self) -> bool;
}

pub struct SystemTerminalDetector;

impl TerminalDetector for SystemTerminalDetector {
    fn is_stdout_tty(&self) -> bool {
        // checks e.g. atty::is(atty::Stream::Stdout)
        true
    }
}

pub struct MockTerminalDetector {
    pub force_tty: bool,
}

impl TerminalDetector for MockTerminalDetector {
    fn is_stdout_tty(&self) -> bool {
        self.force_tty
    }
}
```

## 4. Best Practices Checklist

1.  **Prefer Dependency Injection**: Pass readers/writers (`AsyncRead`/`AsyncWrite`), file paths (`PathBuf`), and config loaders to functions rather than using global state.
2.  **Avoid Parallel Env Mutations**: Do not use `std::env::set_var` without thread-synchronization.
3.  **Perform Reflexive Runs**: Wire property testing directly into commands via compilation flags (`#[cfg(feature = "reflexive-testing")]`) to allow binaries to validate themselves post-deployment.
4.  **Isolate Tempfiles**: Always let `tempfile` clean up directories automatically.
