# Example: wrapping a ggen-generated clap-noun-verb CLI

A CLI generated by `ggen` (via `~/ggen-marketplace/packs/clap-noun-verb-crate-pack`
and its sibling packs -- see `docs/reference/cnv-any.md` in the main crate for
the full ggen-marketplace pack story) is a **native `clap-noun-verb` binary**.
It doesn't strictly need `cnv-any` at all: `clap_noun_verb_deploy::CliSchema::from_command`
already introspects its real `clap::Command` graph directly, in-process, with
perfect fidelity.

This example exists to make one thing explicit: **`cnv-any` doesn't care
whether a target is a native clap-noun-verb binary, a hand-rolled Rust CLI, a
Python script, or a shell script.** The manifest-based path works identically
either way -- it's just usually unnecessary for a native binary, since the
in-process introspection path is more precise (it can't drift from the real
`clap::Command` graph the way a manifest could).

## Files

- `ontology.ttl` -- the **exact same graph**
  `~/ggen-marketplace/packs/clap-noun-verb-zeroconfig-pack` ships (copied
  verbatim), using real behavior kinds (`EchoBehavior`, `ExpressionBehavior`,
  `StaticJsonBehavior`, `RefusalBehavior`) rather than `CustomBehavior` --
  this is the one example whose commands are ALSO compiled to native Rust,
  by the zeroconfig pack, via a completely separate composition of packs.
- `ggen.toml` -- composes `clap-noun-verb-schema-pack` +
  `cnv-any-manifest-pack` only (not the Rust-generating packs) to project
  this same graph into `cnv-any.json`.
- `cnv-any.json` -- **generated**, not hand-typed. Regenerate with:
  ```sh
  ggen sync run
  ```

`cnv-any-manifest-pack`'s projection is behavior-agnostic by design -- it
only ever reads a command's name/about/arguments, never its
`cnv:hasBehavior` -- so the same ontology that compiles to a real Rust
binary via one pack composition projects to a manifest via this one,
without modification.

## Generate the real Rust binary and wrap it both ways

```sh
cd ~/ggen-marketplace/packs/clap-noun-verb-zeroconfig-pack
ggen sync run                       # produces a real Cargo.toml/src/ crate
cargo build --release               # produces target/release/zc
```

**Native path (preferred for a real clap-noun-verb binary):**

```rust
use clap_noun_verb::CommandRegistry;
use clap_noun_verb_deploy::Deploy;

let registry = CommandRegistry::new(); // populated by the generated binary's own #[verb]s
let deploy = Deploy::from_registry(&registry);
```

**cnv-any path (works identically, for comparison/demonstration):**

```rust
let wrapped = clap_noun_verb_any::wrap(
    "~/ggen-marketplace/packs/clap-noun-verb-zeroconfig-pack/target/release/zc",
    Path::new("examples/ggen_generated_rust_cli/cnv-any.json"),
)?;
```

Both produce a `Deploy` that serves identically over MCP/HTTP/Kubernetes/OCI
-- proving `cnv-any`'s manifest path is a strict superset capability (any
executable) rather than a special case that only works for foreign-language
targets.

## Real verified run (this session, not simulated)

Built the real `zc` binary from the zeroconfig pack, wrapped it with
`clap_noun_verb_any::wrap` against this directory's `cnv-any.json`, and ran
a real `greet add 2 3` invocation through the real `Gateway`:

```
argv: ["greet", "add", "2", "3"]
stdout: "5\n"
OK: wrapped real ggen-generated zc binary via cnv-any through the real Gateway
```

The wrapped invocation's real subprocess output matched the native binary's
own direct output (`./target/release/zc greet add 2 3` also prints `5`),
confirming the two paths are behaviorally identical.
