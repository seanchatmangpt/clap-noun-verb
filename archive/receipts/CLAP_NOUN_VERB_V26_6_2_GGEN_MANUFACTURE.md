## Manufacturing Overview

The clap-noun-verb framework uses **ggen** (code generation) to manufacture command implementations from **source law** (ontologies) and **templates**.

**Manufacturing Doctrine:** All code is derived from declarative specifications (RDF/Turtle ontologies) via SPARQL queries and Jinja2 templates. The pipeline emits receipts (SHA256 artifact hashes) proving artifact provenance.

## Stage Configuration

### Stage 1: Specification Extraction

**Query:** `queries/generate-cli-spec.rq`  
**Input:** Ontology sources (RDF/Turtle)  
**Output:** `src/generated/cli_spec.json`  
**Format:** JSON

**Purpose:** Extract command specifications (noun names, verb names, arguments, return types) from ontology.

**Ontology Sources:**
- `ontology/clap-noun-verb-ontology.ttl` — Core CLI domain model
- `ontology/cli-pattern.ttl` — Noun-verb pattern definitions
- `ontology/verb-traits.ttl` — Trait specifications
- `ontology/ggen-command-vocab.nt` — Code generation vocabulary
- `ontology/cargo-cicd.ttl` — cargo-cicd domain model (future integration)

**Example Output:**
```json
{
  "commands": [
    {
      "noun": "services",
      "verb": "status",
      "arguments": [
        { "name": "service_id", "type": "String", "required": true }
      ],
      "return_type": "ServiceStatus",
      "output_format": "json"
    }
  ]
}
```

### Stage 2: Validation (Conformance Check)

**Query:** `queries/validate-cli-structure.rq`  
**Input:** Ontology sources + extracted specs  
**Output:** `src/generated/validation_report.json`  
**Format:** JSON  
**Severity:** Error (blocks pipeline on failure)

**Validation Rules:**
- ✓ All nouns have descriptions (cnv:nounAbout)
- ✓ All verbs have descriptions (cnv:verbAbout)
- ✓ No orphaned terms (all terms referenced)
- ✓ Return types are Serialize-compatible
- ✓ Argument types are valid Rust types

**Example Report:**
```json
{
  "valid": true,
  "errors": [],
  "warnings": [],
  "total_terms": 42,
  "valid_terms": 42
}
```

---

### Stage 3: Trait Implementation Generation

**Query:** `queries/generate-trait-impls.rq`  
**Template:** `templates/verb.rs.jinja`  
**Output Pattern:** `src/generated/verbs/{noun_name}/{verb_name}.rs`  
**Format:** Rust code  
**Severity:** Error (blocks pipeline on failure)

**Template Mappings:**
- `noun_name` → `cnv:hasNounName`
- `noun_description` → `cnv:nounAbout`
- `verb_name` → `cnv:hasVerbName`
- `verb_description` → `cnv:verbAbout`
- `return_type` → `cnv:returnType`
- `arguments` → `cnv:hasArguments`
- `output_format` → `cnv:outputFormat`

**Example Generated Module:**
```rust
// Generated by ggen from ontology/clap-noun-verb-ontology.ttl
// DO NOT EDIT

use clap_noun_verb::{verb, HandlerInput, HandlerOutput, Result};
use serde::Serialize;

#[derive(Serialize)]
pub struct ServiceStatus {
    pub running: bool,
    pub uptime_ms: u64,
}

#[verb(noun = "services", name = "status", about = "Show service status")]
pub fn status(#[arg] service_id: String) -> Result<HandlerOutput<ServiceStatus>> {
    Ok(HandlerOutput::new(
        ServiceStatus { running: true, uptime_ms: 0 },
        0,
    ))
}
```

### Stage 5: Test Generation

**Template:** `templates/cli_test.rs.jinja`  
**Output Pattern:** `tests/generated/{noun_name}_{verb_name}_test.rs`  
**Format:** Rust test code  
**Severity:** Warning (does not block pipeline)

**Generated Test Structure (AAA Pattern):**
- **Arrange:** Set up test fixtures and inputs
- **Act:** Call the verb handler with test inputs
- **Assert:** Verify output, status code, and side effects

**Example Generated Test:**
```rust
#[test]
fn test_services_status_returns_ok_when_service_exists() {
    // Arrange
    let service_id = "web-01".to_string();
    
    // Act
    let result = status(service_id);
    
    // Assert
    assert!(result.is_ok());
    let output = result.unwrap();
    assert_eq!(output.exit_code, 0);
    assert!(output.data.running);
}
```

## Proof Gates (Quality Checks)

| Gate | Enabled | Severity | Check |
|------|---------|----------|-------|
| **Ontology Consistency** | Yes | Error | All nouns and verbs must have descriptions |
| **Code Compilation** | Yes | Error | Generated code must pass `cargo check` |
| **Test Coverage** | Yes | Warning | Minimum 50% coverage (auto-generated tests) |
| **Documentation** | Yes | Warning | All verbs must have doc comments |

**Failure Behavior:**
- **Error gates:** Pipeline stops, artifacts not released
- **Warning gates:** Pipeline continues, violations recorded in report

## Execution Pipeline

### Dependency Graph
```
spec_extraction
    ↓
validation
    ├→ trait_generation
    │   ├→ documentation ──→ test_generation
    │   └→ test_generation
    └→ documentation
```

### Execution Order
1. `spec_extraction` — Extract command specs from ontologies
2. `validation` — Verify specs are valid (error gate)
3. `trait_generation` — Generate handler code (depends on specs)
4. `documentation` — Generate markdown docs (depends on specs, parallelizable)
5. `test_generation` — Generate test cases (depends on specs + handlers, parallelizable)

### Parallelization
**Parallelizable Stages:** documentation, test_generation (no shared output dependencies)

## SPARQL Query Registry

### 1. generate-cli-spec.rq
**Purpose:** Extract command specifications from ontology  
**Returns:** Noun names, verb names, argument lists, return types  
**Output:** `src/generated/cli_spec.json`

### 2. find-all-verbs.rq
**Purpose:** Discover all registered verbs  
**Returns:** Verb URIs, names, descriptions  
**Usage:** Validation, documentation generation

### 3. extract-arguments.rq
**Purpose:** Extract parameter definitions for a verb  
**Returns:** Argument names, types, defaults, constraints  
**Usage:** Handler code generation

### 4. validate-cli-structure.rq
**Purpose:** Conformance check (proof gate)  
**Returns:** Valid/invalid status, error list  
**Severity:** Error (blocks pipeline on validation failure)

### 5. generate-trait-impls.rq
**Purpose:** Generate trait implementation signatures  
**Returns:** Method signatures, type bindings  
**Usage:** Trait generation stage

### 6. cargo-cicd-commands.rq
**Purpose:** Extract cargo-cicd domain commands (future)  
**Returns:** CI/CD command specifications  
**Usage:** ci/cd command manufacturing

## Template System

**Engine:** Jinja2  
**Template Directory:** `templates/`

### Available Templates

#### verb.rs.jinja
Generates Rust handler functions with `#[verb]` macro.

**Variables:**
- `noun_name` — Noun identifier
- `verb_name` — Verb identifier  
- `verb_description` — Doc comment
- `arguments` — List of arguments with types
- `return_type` — Serializable return type
- `output_format` — JSON/other format

#### command_doc.md.jinja
Generates markdown documentation for a command.

**Variables:**
- `noun_name`, `verb_name`, `description`
- `arguments` with defaults and constraints
- `return_type` with example JSON output
- `usage_example` — CLI invocation example

#### cli_test.rs.jinja
Generates test module with AAA pattern tests.

**Variables:**
- `test_name` — Descriptive test function name
- `arrange_code` — Fixture setup
- `act_code` — Handler invocation
- `assert_code` — Assertions
