## Preamble

The separation of public teaching from protected machinery is a foundational discipline. Public surfaces tell the story of our doctrine and governance. Protected machinery provides competitive advantage and operational security.

This law defines:
1. What may be exposed on each public surface
2. What must remain protected machinery
3. How to classify new artifacts
4. What constitutes a boundary violation
5. How violations are remediated
6. The appeals process

**Violation of this law is a defect.** It must be caught, fixed, and prevented from recurring.

## TITLE I: DEFINITIONS

### Section 1.1: Public Surface
A **public surface** is any artifact designed for external consumption or team-wide visibility:
- LinkedIn posts
- Newsletter articles
- Landing page copy
- Manifesto sections
- Documentation (public canon)
- Architecture diagrams (C4)
- Project definitions (SPR)
- Gate assignments
- Nehemiah progress tracking
- TOGAF mappings

### Section 1.2: Protected Machinery
**Protected machinery** is implementation detail, algorithm logic, or operational data that provides competitive advantage or reveals proprietary methodology:
- Wasm4pm algorithm code
- Ggen rendering templates
- Prompt Manufactory internals
- Wasm4pm-compat type law
- Private deployment configurations
- Internal receipt formats (pre-publication)
- Unpublished research graphs
- Competitive advantage details
- Internal audit logs
- Unpublished doctrinal content

### Section 1.3: Reference vs. Exposure
- **Reference:** Discussing a protected component conceptually (allowed)
  - Example: "Wasm4pm uses process mining to optimize execution"
  - Example: "Prompt Manufactory guides research via LLM"
- **Exposure:** Showing implementation details, code, algorithms, or specifics (forbidden)
  - Example: Publishing wasm4pm algorithm source
  - Example: Revealing prompt structures or templates
  - Example: Showing deployment configuration details

### Section 1.4: Classification Authority
**Classification** (assigning a surface to "public" or "protected") is performed by:
- Primary: Sean Chatman (Doctrine Keeper)
- Secondary: Domain experts (architect, researcher, operations lead)
- Process: Review pre-publication; challenge post-publication via inspection

### Section 1.5: Boundary Violation
A **boundary violation** occurs when:
1. Protected machinery is exposed on a public surface
2. Protected data is stored in a public repository
3. Proprietary methodology is revealed without authorization
4. Competitive advantage is leaked through teaching or documentation
5. Receipt format is published before authorization
6. Unpublished research is disclosed prematurely

**Consequence:** Immediate remediation, audit, prevention plan.

## TITLE IV: BOUNDARY CLASSIFICATION PROCESS

### Section 4.1: Artifact Classification Workflow

**Step 1: Creation**
Author identifies artifact type and intended audience:
- LinkedIn post → Public surface
- Algorithm code → Protected machinery
- Newsletter article → Public surface
- Research data → Protected machinery

**Step 2: Pre-Publication Review**
- **Light:** Self-review (LinkedIn, simple updates)
- **Medium:** Peer review (newsletter, landing page)
- **Heavy:** Doctrine review (manifesto, gate assignments)

**Step 3: Classification Decision**
Reviewer confirms:
- ✅ No protected machinery exposed
- ✅ Exposure level matches surface type
- ✅ All forbidden content removed or abstracted
- ✅ References are conceptual, not code/config

**Step 4: Publication**
Author publishes with confidence boundary is protected.

**Step 5: Audit (Post-Publication)**
Monthly scan of all public surfaces for accidental exposure.

### Section 4.2: New Artifact Classification Template

When creating a new artifact, answer:

1. **What is this artifact?** (Type)
2. **Who is the audience?** (Public / Private / Team-specific)
3. **What protected machinery does it reference?** (List)
4. **Is each reference conceptual or code-level?** (Check)
5. **What forbidden content was removed?** (Document)
6. **Who reviews before publication?** (Authority)
7. **What audit will verify boundary integrity?** (Plan)

## TITLE V: VIOLATION DETECTION AND REMEDIATION

### Section 5.1: Violation Types

**Type A: Code Exposure**  
Protected algorithm, configuration, or template code appears in public repository or public documentation.

**Type B: Format Exposure**  
Protected schema, structure, or encoding details appear in public artifact.

**Type C: Methodology Exposure**  
Proprietary methodology, algorithm steps, or optimization tricks are revealed without authorization.

**Type D: Competitive Intelligence Leak**  
Performance metrics, pricing logic, or market positioning is disclosed prematurely.

**Type E: Timing Leak**  
Research or features are disclosed before planned publication/release date.

**Type F: Configuration Leak**  
Deployment details, infrastructure, credentials, or operational configuration is exposed.

**Type G: Audit Log Leak**  
Internal audit trails, decision records, or sensitive operational data is disclosed.

### Section 5.2: Violation Detection

**Manual Audits (Monthly):**
- Scan LinkedIn posts for protected machinery references
- Review newsletter articles for over-exposure
- Check landing page copy for technical leaks
- Verify C4 diagrams contain no code details
- Audit gate assignments for sensitive data
- Review Nehemiah posts for resource allocation details

**Automated Checks (Pre-Publication):**
- Lint scripts check for protected keywords (algorithm code, credentials, etc.)
- Review checklist verifies all forbidden content is removed
- Diff audit confirms no protected files added to public repo

**Community Reports:**
- Team members can report suspected violations
- Security review process for sensitive findings

### Section 5.3: Violation Response Protocol

**Upon Detection:**

1. **Immediate Containment** (within 24 hours)
   - Remove exposed content from public surface
   - Disable public access (if applicable)
   - Notify Doctrine Keeper and domain expert

2. **Assessment** (within 48 hours)
   - Determine violation type and severity
   - Assess if competitive advantage is compromised
   - Evaluate customer/team impact
   - Check if malicious disclosure occurred

3. **Remediation** (within 1 week)
   - Rewrite artifact to remove exposure
   - Audit similar artifacts for same issue
   - Re-classify artifact if necessary
   - Add protection to prevent recurrence

4. **Prevention** (ongoing)
   - Update review process if gap identified
   - Add lint rule or automated check
   - Retrain team if needed
   - Document lesson learned

5. **Documentation** (archive)
   - Record violation type, severity, remediation
   - Update boundary rules if necessary
   - Update audit process if necessary

### Section 5.4: Violation Severity Levels

**Level 1: Minor (Low Impact)**  
- Conceptual reference to protected machinery in wrong context
- Minor exposure that does not compromise competitive advantage
- Remediation: Rewrite and republish within 1 week

**Level 2: Moderate (Medium Impact)**  
- Methodology hints or partial exposure
- Limited competitive advantage impact
- Requires domain expert remediation
- Remediation: Investigation + rewrite + prevention within 2 weeks

**Level 3: Severe (High Impact)**  
- Algorithm code or key implementation details exposed
- Clear competitive advantage compromise
- Requires immediate containment and leadership review
- Remediation: Containment + investigation + strategy adjustment within 1 week

**Level 4: Critical (Extreme Impact)**  
- Widespread exposure across multiple surfaces
- Irreversible competitive advantage loss
- Requires executive decision and incident response
- Remediation: Full response plan, post-incident review, strategy pivot

## TITLE VI: APPEALS AND EXCEPTIONS

### Section 6.1: Challenge Process

If a creator believes artifact is over-classified (too protective):

1. **Submit Challenge:** Document why exposure is needed
2. **Review:** Doctrine Keeper + domain expert evaluate
3. **Decision:** Approve (reclassify) or deny (maintain protection)
4. **Communication:** Explain reasoning to creator

### Section 6.2: Emergency Disclosure

If operational emergency requires exposing protected machinery:

1. **Request:** Document emergency, duration, scope
2. **Approval:** CEO + Doctrine Keeper dual approval required
3. **Limitation:** Exposure limited to minimum necessary, shortest duration
4. **Audit:** Post-incident review and boundary restoration
5. **Prevention:** Plan to avoid future emergencies

### Section 6.3: Academic/Community Sharing

If publishing academic research or sharing with community:

1. **Timeline:** Plan publication date early (6+ months advance)
2. **Coordination:** Align with product release schedule if applicable
3. **Anonymization:** Remove proprietary details or delay publication
4. **Authorization:** Doctrine Keeper approval required before submission
5. **Timing:** Coordinate with customer announcements if applicable

### Section 6.4: Regulatory Disclosure

If required by law or regulation to disclose protected information:

1. **Legal Review:** Confirm disclosure requirement
2. **Scope Limitation:** Disclose only legally mandated information
3. **Protection:** Use confidentiality agreements and limited distribution
4. **Documentation:** Record disclosure and authorization
5. **Restoration:** Return to full protection once legal requirement expires
